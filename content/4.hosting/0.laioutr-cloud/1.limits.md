Every figure on this page is enforced by the platform. Where a limit depends on your plan, the plan
column says so.

## Builds

| Limit | Value | What happens |
| --- | --- | --- |
| Duration | 20 minutes | The build is stopped and the deployment fails. A build that runs this long is stuck — a working storefront build finishes in single-digit minutes. |
| Retries | none | A failed build is not retried. Fix the cause and deploy again. |
| CPU | 7 vCPU, dedicated | The build has a node to itself. |
| Memory | 12 GiB | Node exits with a heap error. The build runs with `--max-old-space-size=8192`. |
| Project bundle | 100 MB, uncompressed | The deployment is refused before anything is uploaded, and its error states the bundle's size. Contact Laioutr support. |
| Concurrent builds | 2 per platform | A third build waits until one of the two finishes. It is not queued on a node, so it costs nothing while it waits. |
| Log size | 5 MB | The rest of the log is cut, with a marker at the end. |
| Log retention | 7 days after the build ends | The deployment API answers with an empty log after that. Logs are archived when the build finishes; the build's own pod is removed an hour after it ends. |
| Dependencies | installed fresh | Every build downloads every dependency. The bundle carries no lockfile, so a build can resolve newer versions than the last one. |
| Bundle retention | 7 days | The uploaded project is deleted. It is read once, by the build, so nothing afterwards depends on it — a rollback re-promotes a built image and never rebuilds. |

A build runs on its own node, which is destroyed when the build ends. It reaches the internet the way
a build does anywhere else — your own registry, a Git dependency, a `postinstall` script that fetches
a prebuilt binary all work. It cannot reach anything inside the platform: no other tenant, no node, no
metadata service.

Your environment variables are readable by everything that runs during the build, including the
install scripts of every package you depend on. That is true of every build platform. Give a build
only the credentials it needs.

## Running storefronts

A size class fixes the shape of one pod. How many pods you get follows from the page views your plan
covers, so a larger plan on the same class means more pods, not bigger ones.

Up to a few million page views a month the minimum pod count already covers the traffic: two pods for
S, three for M and L. Above it the count grows with your allowance.

| | S | M | L |
| --- | --- | --- | --- |
| CPU reserved | 0.5 vCPU | 1 vCPU | 1 vCPU |
| CPU ceiling | 2 vCPU | 2 vCPU | 2 vCPU |
| Memory reserved | 768 MiB | 768 MiB | 1536 MiB |
| Memory ceiling | 2 GiB | 2 GiB | 3 GiB |
| JavaScript heap | 1,536 MiB | 1,536 MiB | 2,304 MiB |
| Writable disk | 1 GiB | 1 GiB | 2 GiB |
| Adds pods under load | no | yes | yes |
| Preview deployments awake at once | 5 | 5 | 10 |

**S does not scale out.** A spike makes an S storefront slower and never more expensive. M and L add
pods up to a ceiling derived from your page-view allowance.

An S storefront runs at least 2 pods, M and L at least 3, and the platform spreads them across separate
machines wherever the cluster has machines to spread them over.

The JavaScript heap is 75 % of the memory ceiling; the rest is for Node itself. A storefront that
outgrows it stops with `JavaScript heap out of memory` and restarts.

### Per request

| Limit | Value | What happens |
| --- | --- | --- |
| Request timeout | 125 seconds | The edge answers 524. Anything that takes longer belongs in a background job. |
| Request body | 100 MB | The edge answers 413 before the request reaches your storefront. Upload large files to storage directly. |
| Streams and WebSockets | 300 seconds | The connection closes. Reconnect from the client. |
| Startup | 120 seconds | A pod that has not answered its health check by then is restarted. At build time the limit is 60 seconds, and the deployment fails. |
| Rate limit | derived from your class and pod count | Excess requests get 429. It sits at roughly twice what your pods can serve, so ordinary traffic never reaches it. |
| Shutdown grace | 60 seconds | A request in flight while a pod is replaced gets this long to finish; a longer one is cut. |

### Outgoing requests

Your storefront can reach any public address. Pods on one machine share its outgoing IP address, so an
upstream API that limits requests per IP counts your storefront together with others on the same machine.
A fixed outgoing address is not available yet.

### Configuration

There are no runtime environment variables. Your project's configuration is built into the image, so
changing a value means a new deployment.

### Storage and state

Write only to `/tmp`, and only as a scratch space. The writable disk in the table above is the
ceiling; a pod that exceeds it is evicted. **Nothing written by a storefront survives a restart, and
pods are replaced routinely.** The shared cache is a cache: an entry can be evicted at any time, so never
keep state there that you cannot rebuild.

A storefront cannot create a load balancer, open a node port, or claim a disk. Those are billable
resources, and the platform creates none of them on your behalf.

### Hostnames

Every storefront gets a permanent hostname of the platform's own from the day it is created,
`<name>.laioutr.app`, and that hostname serves production whether or not you have connected a domain.
Laioutr assigns the name when the storefront is created and keeps it for good, also when the project is
renamed. Once one of your own domains is canonical, the platform hostname answers
`X-Robots-Tag: noindex`, so the two never compete for the same content in search results.

### Preview deployments

Every deployment has a hostname of its own, `<name>-<9 characters>.laioutr.app`, for as long as it is
kept. A deployment that is no longer kept answers with a not-found page.

| Kept | For how long |
| --- | --- |
| Production deployments you replaced | the last 2, for 24 hours — the window for a rollback without a rebuild |
| Named previews | the newest deployment of each name, until you delete it |
| Unnamed previews | 14 days |
| All previews together | at most 10; the oldest goes first |

A preview that nobody visits scales to zero after 5 minutes and wakes on the next request, so the first
request to a cold preview is slower. Beyond the number of previews awake at once in the table above, a
preview answers 504 after about 15 seconds until another one sleeps. Preview hostnames are never
indexed.

## Suspension

A suspended storefront keeps its hostnames and its images, answers every request with a holding page,
and runs no pods. Nothing is deleted.
