# Writing Style Guide

Detailed style rules for Laioutr technical documentation. Referenced by the main `technical-writing` skill.

## Voice & Tone

### Second Person Always

Address the reader as "you". Never use "the developer", "one", "users", or "we".

```markdown
<!-- BAD -->
The developer can configure webhooks in the Cockpit settings.
One should ensure the API key has sufficient permissions.

<!-- GOOD -->
You can configure webhooks in your [Cockpit settings](https://cockpit.laioutr.cloud/o/_/p/_/settings).
Make sure your API key has sufficient permissions.
```

### Active Voice

The subject performs the action. Passive voice obscures who does what.

```markdown
<!-- BAD (passive) -->
The frontend is generated by Laioutr when a deployment is triggered.
The cart is updated when the action is dispatched.

<!-- GOOD (active) -->
Laioutr generates the frontend when you trigger a deployment.
The action dispatches and updates the cart.
```

### Docker-Style Conversational

Use analogies, rhetorical questions, and scenario-based intros. Write like you're explaining to a colleague, not writing a textbook.

```markdown
<!-- BAD (textbook) -->
Orchestr is a data composition framework that enables server-side data fetching
through configurable handlers.

<!-- GOOD (conversational) -->
Your storefront needs data from three different APIs - products from your PIM,
prices from your commerce platform, and inventory from your warehouse. Orchestr
lets you compose all of that into a single response, server-side, before the
page even loads.
```

### Celebrate Success

At key milestones, acknowledge what the reader has accomplished.

```markdown
Your storefront is now live! Visitors to your domain will see the Laioutr-generated
frontend with your commerce data.

That's it - your Orchestr action is handling cart updates. Every time a customer
adds a product, your handler processes the request.
```

### Honest About Complexity

Don't gloss over difficult parts. Acknowledge complexity and guide through it.

```markdown
This next part involves coordinating three services, so take it step by step.
If something goes wrong, check the troubleshooting section at the end.
```

## Structure

### Front-Load Important Information

Put the most critical information first. Developers scan - they don't read linearly.

```markdown
<!-- BAD: buries the key info -->
Laioutr's deployment system uses a build pipeline that processes your frontend
code through several stages. The build typically takes 2-5 minutes. You can
monitor the build status in the Cockpit. **If the build fails, check the
build logs for errors.**

<!-- GOOD: key info first -->
**If your build fails**, check the build logs in the
[Cockpit](https://cockpit.laioutr.cloud/o/_/p/_/settings) for errors.
Builds typically take 2-5 minutes and process through several pipeline stages.
```

### Heading Frequency

Add a heading every 2-4 paragraphs. Long unbroken sections lose readers.

### Paragraph Length

Maximum 3-4 sentences per paragraph. Break up dense content.

### Bold Key Terms

Bold a term on its first use when introducing it.

```markdown
Laioutr uses **Orchestr** to compose data from multiple sources server-side.
Each data source is connected through an **action handler** that you define.
```

### End Sections with Next Steps

Guide the reader to related content at section boundaries.

```markdown
Now that your action handler is working, you can [add error handling](/frontend/orchestr/error-handling)
or [connect additional data sources](/frontend/orchestr/data-sources).
```

## Code Examples

### Code Within First 3 Paragraphs

Every how-to guide and tutorial must show code early. Don't make readers wade through explanation first.

### Copy-Pasteable

All examples must work when pasted directly. Use realistic Laioutr domain values.

```typescript
// BAD: placeholder values
const result = await myAction({ foo: 'bar' });

// GOOD: realistic Laioutr values
const result = await addToCart({
  productId: 'nike-air-max-90',
  quantity: 1,
  variantId: 'size-42-black',
});
```

### Code Groups for Multi-Environment

Use `::code-group` when showing the same operation across package managers or environments.

```markdown
::code-group
```bash [pnpm]
pnpm add @laioutr-core/orchestr
```
```bash [npm]
npm install @laioutr-core/orchestr
```
```bash [yarn]
yarn add @laioutr-core/orchestr
```
::
```

### Twoslash for TypeScript

Use twoslash annotations to show inferred types. Invoke `technical-writing-code-examples` for quality enforcement.

### Show Expected Output

After every executable example, show what the reader should see.

```markdown
You should see output like:

```json
{
  "status": "success",
  "cartId": "cart-a1b2c3",
  "itemCount": 1
}
```
```

## Cross-Linking

### Relative Paths

Link to other documentation pages using relative paths.

```markdown
For more on action handlers, see [Orchestr Actions](/frontend/orchestr/actions).
```

### Cockpit Links

Use the `_` placeholder pattern for organization and project slugs.

```markdown
Configure this in your [Cockpit settings](https://cockpit.laioutr.cloud/o/_/p/_/settings).
Manage API keys in the [API keys page](https://cockpit.laioutr.cloud/o/_/api-keys).
Open the [Studio](https://cockpit.laioutr.cloud/o/_/p/_/studio) to edit visually.
```

### Link Don't Explain

Never explain a concept that has its own dedicated page. Link to it.

```markdown
<!-- BAD: re-explaining Orchestr -->
Orchestr is Laioutr's data composition framework. It allows you to define
action handlers that fetch data from external APIs and compose them into a
unified response. To use Orchestr with your commerce data...

<!-- GOOD: link to the concept page -->
Use [Orchestr](/frontend/orchestr) to compose your commerce data into a
unified response.
```

## Prohibited Patterns

### Marketing Language

Never use: "powerful", "seamless", "cutting-edge", "robust", "enterprise-grade", "next-generation", "best-in-class", "world-class".

### Passive Voice

Rewrite every passive sentence to active voice unless the subject genuinely doesn't matter.

### Walls of Text

Every section longer than 2 paragraphs without code, a table, or a visual element needs restructuring.

### Placeholder Values

Never use foo, bar, baz, myVariable, exampleFunction, test123. Use Laioutr domain examples: product names, cart actions, Orchestr queries, real component names.

### READMEs and End-User Guides

This skill produces technical documentation only. Use other tools for READMEs, changelogs, billing docs, or Cockpit UI walkthroughs.
